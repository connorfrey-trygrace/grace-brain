# Workflow: Text Message Sync

Procedure for scanning Connor's text messages (iMessage/SMS) for Grace-relevant content and folding the findings into the existing trackers. **Runs once daily at 8:00 AM via the scheduled task `grace-text-scan`** (cron `0 8 * * *`), and can also be run **on-demand** any time Connor asks (e.g. "scan my texts"). Every run is **incremental** — it processes only messages newer than the `## Last scan` marker, so nothing is scanned twice. **Discretion in automated runs:** only clearly-safe additive findings are folded into trackers automatically; sensitive/personnel content and any contradictions are *surfaced in the run report for Connor to decide*, never auto-written.

This exists because Grace staff and vendors text important logistics, decisions, and asks about as often as they email — so texts are a real source alongside [[CLAUDE.md]] transcripts, not a substitute for them.

## Source & access

- The source is the macOS Messages database, `chat.db`, inside the mounted `~/Library/Messages` folder. Messages writes live to `chat.db` plus its `-wal` / `-shm` sidecars.
- **Mount path (bash):** `/sessions/<session>/mnt/Library--Messages/chat.db` (e.g. this run: `/sessions/upbeat-beautiful-feynman/mnt/Library--Messages/chat.db`). The `/sessions/.../` prefix changes each session; the `mnt/Library--Messages/` tail is stable. **Corrected 2026-07-24** — this section previously named the `mnt/Messages/` mount, which only exposes `/System/Library/Messages` (app resources, no `chat.db`); the real database lives under the `~/Library/Messages` mount, which the session maps to `mnt/Library--Messages/`. The wrong path caused two consecutive false "mount unavailable" errors earlier today (13:33, 13:43 ET runs) before this was caught.
- The mount may require **Full Disk Access** for the Claude app (System Settings → Privacy & Security → Full Disk Access). If a scan reads as empty or permission-denied, that's the first thing to check.
- **Never open the live database in read/write mode.** Copy `chat.db` (and sidecars if present) to the sandbox tmp first, or open with a read-only URI (`file:chat.db?immutable=1`). This avoids corrupting or locking the database Messages is actively using.
- **Never touch the `Attachments` subfolder.** It can be many GB of photos/video and is out of scope. Read `chat.db` only.

## Privacy & discretion

The mount exposes *all* of Connor's texts, not just Grace ones. Two standing rules:

- Only surface and record **Grace-relevant** content. Personal/unrelated messages are read past, never quoted, never written anywhere.
- Some Grace texts are shared in confidence. Anything folded into a Dropbox-synced tracker should be logistics/decisions/asks — not sensitive personal disclosures. When in doubt, surface it to Connor in chat and let him decide rather than writing it down.

## Exclusions (hard skip — applied before any decode)

Some threads are **never** to be read, decoded, or surfaced. Exclusion is enforced at the SQL level: filter out the excluded handle(s) / chat(s) in the query so their message bodies are never returned. This is not a "read then ignore" — excluded content is never seen.

Excluded contacts:
- **Sky** — handle: `9087980030`. Exclude the **1:1 / direct thread only**. Match on the last 10 digits (handles in `chat.db` may be stored as `+19087980030`, `9087980030`, etc.).

Scope of the Sky exclusion:
- **Direct (1:1) thread with Sky → never read, decode, or surface.** Enforced at the SQL level.
- **Group chats that include Sky → OK to scan.** Per Connor, only the private 1:1 messages are off-limits; group threads (including any with Grace people) are in scope and processed normally.

## Step 1: Determine scan window (incremental)

Read the **## Last scan** section at the bottom of this file for the last-synced `ROWID` and date. Scan only messages with a higher `ROWID` (i.e. new since last run). If there is no recorded marker (first run), scan full history per Connor's standing choice.

## Step 2: Extract and decode

- Query `message` joined to `handle` and `chat` for: `ROWID`, contact handle (phone/email), `is_from_me`, `date` (Apple epoch — convert: nanoseconds since 2001-01-01), `text`, and `attributedBody`.
- **Timezone — convert to Connor's local Eastern time before reporting.** `date` is stored in **UTC**. A naive epoch→datetime gives UTC, which is **4h ahead of EDT (5h ahead of EST)** — so an 8:43 AM ET text renders as 12:43 without conversion. Always convert UTC → `America/New_York` (DST-aware) so text times line up with meeting-recording filenames (which are already local) and with Connor's recollection. (Caught 2026-06-25: a morning text mislabeled as midday made it look like it came *after* a call it actually prompted.)
- On recent macOS the `text` column is often NULL and the message body lives in `attributedBody` (an NSAttributedString typedstream blob). Decode it to recover the text.
- If a message body can't be cleanly decoded, **flag it as garbled — do not guess at the content.** Note the contact and timestamp so Connor can check the thread himself.

## Step 3: Resolve contacts to names

> 🛑 **Run the script. Do not hand-roll a grep.**
> ```
> python3 "Workflows/resolve-phone.py" 434-996-6618 "(704) 956-4975" ...
> python3 "Workflows/resolve-phone.py" --audit     # vCard health check
> ```
> [[Workflows/resolve-phone.py]] checks every source below in authority order and is the **only** approved resolution method. It exists because grepping for a number as formatted in the Phone-Index silently missed **18% of vCard entries** (format blindness — `(434) 996-6618` never matches a search for `434-996-6618`) and, worse, **34% of TEL lines are malformed** in a way that makes naive last-10-digit extraction return a *confidently wrong* number. That combination hid Jake Lindo, Logan Aldridge, and Tyler Dressler for weeks, and defeated the 2026-07-17 `phone:`-property fix entirely. Full measurements in [[Contacts/Phone-Index]]'s 2026-07-28 changelog.
>
> The script never invents a name: it reports `phone:`-property notes, the Phone-Index **Confirmed** table, the Office list, and the vCard as identifications, and anything else as a **mention only**. A number appearing in a sync's own run notes is not an identification.

Map phone numbers / emails to real names so threads are identifiable. Sources, in authority order (all of these are what the script checks — the list is the spec, the script is the implementation):

- [[Contacts/Phone-Index.md]] — number→name cache; **check this first** (fastest, covers non-staff like cohort members/volunteers identified in prior scans).
- **Any `*.vcf` in `Contacts/`** (newest by mtime wins; macOS auto-names the export e.g. `Connor Frey and 614 others.vcf`) — an exported vCard of Connor's macOS Contacts (~625 numbers as of 2026-06-25). Parse for `TEL` ↔ `FN` matches on last 10 digits. Optional and may be stale; Connor re-exports periodically. The live Contacts DB can't be mounted (macOS protects `Library/Application Support`), so the export is the substitute. **Note:** the contact's card name is used verbatim (e.g. "Seth-Worship Addison"); normalize to the canonical Office spelling when writing to trackers.
- `Dropbox/Office/` Grace Org Chart.pdf + Staff Contact List.xlsx (canonical name authority — wins on any conflict with the index/export).
- [[Contacts/Vendors.md]] for vendor numbers.
- **Any vault note with a `phone:` frontmatter property** — e.g. the Boot Camp leader notes under `Events/2026-07-29-Boot-Camp/Leaders/`. Search the vault for the last 10 digits (grep, digits-only normalization) before declaring a number unknown. Added 2026-07-17 after the **second** miss of this kind: Kirk Salvary (7/6) and Brandon Brys (7/3→7/17) both sat on the watchlist for days while their numbers were already recorded in roster/leader notes this list didn't cover.
- Memory: confirmed Grace staff contacts; spelling rules (e.g. "Jean Paul" not "John Paul", "Steve Coy" not "Koy").

**When a scan newly resolves a number** (via export, Office list, or Connor confirming it), append it to the **Confirmed** table in [[Contacts/Phone-Index.md]] (additive: date + how confirmed) so the next run resolves it automatically. Mark inferred/unconfirmed matches as such — don't promote a guess to Confirmed.

**If a number still can't be resolved**, do two things: (a) keep the raw handle and surface it in the run report — an unknown number texting Grace logistics is itself worth surfacing; and (b) **add it to the "Unconfirmed / inferred" section of [[Contacts/Phone-Index.md]]** (number + thread/context + date first seen). That section is a standing **re-resolution watchlist**, not a dead end (see the re-resolution pass below). This matters because scans are incremental: once a handle is flagged unknown, no later run revisits that message, so without a watchlist a number stays unknown forever — even after Connor adds the contact. (Exactly what happened 6/25–6/26: Brandon Geddes / Simba Kanjanda were flagged unknown because the vCard export (mtime 6/25 21:45) post-dated the scan that hit them; Connor's later export could resolve them, but nothing re-ran resolution, so the seeding-completion they evidenced went unconnected.)

### Step 3.5: Re-resolution pass (run at the START of every scan, before Step 4)

Re-check every number in the Phone-Index **"Unconfirmed / inferred"** watchlist by passing the whole watchlist to `resolve-phone.py` in one call — that is the entire pass, and it takes seconds. (Historically this step was done by eye and by grep, which is why it produced three false "unknown" verdicts on contacts that were already in the vault.) Sources checked: vCard export + Office list + Vendors + `phone:`-property notes + Phone-Index Confirmed + memory. **Trigger especially when the newest `*.vcf` mtime is newer than this workflow's last run** — that means Connor re-exported contacts and previously-unknown numbers may now resolve. For each that now resolves: move it to the **Confirmed** table (date + how confirmed), drop it from the watchlist, and **retro-tie it to any tracker item or note where its earlier (unknown-flagged) messages belong** (additively — and record a closure candidate if that retro-tie now evidences a completed item). Leave still-unknown numbers on the watchlist for the next run.

## Step 4: Filter for Grace-relevant content

A message qualifies if it references any of:

- A known Grace person (staff/vendor/volunteer) discussing church matters
- An event by name or its logistics (World Cup party, Rend Collective concert, Sunday-night service, etc.)
- A decision, commitment, deadline, date, time, or location tied to Grace work
- An action item — something Connor (or someone else) needs to do
- A vendor/credential/cost detail

Casual or unrelated personal messages do not qualify. **Do not fabricate** relevance or content — if it isn't clearly in the message, it doesn't go in.

## Step 5: Fold into trackers (additive only)

Per Connor's standing choice, findings go into the existing trackers — **not** a separate text-log note.

- **Action items** → create (or update) a note in `/Trackers/Actions/` per [[Workflows/Open-Actions-Tracker]]'s item schema (frontmatter: status, priority, owner, added, deadline, etc.; body keeps the same bulleted fields as before — Priority, Source, Added, Deadline, Status, Last mentioned, Notes, Blocked by). For **Source**, cite the text: `Text from {Name}, {YYYY-MM-DD}` (there is no transcript file to link).
- **Event details** (dates, logistics, vendor info) → the relevant [[Events]] note.
- **Additive rule:** only add or append. Never subtract, overwrite, or "correct" existing tracker content based on a text — if a text contradicts the tracker, surface the conflict to Connor, don't silently resolve it. (See memory: push notes additively.)
- If a finding would duplicate an item already tracked, append a dated note to the existing note's body (e.g. "6/23 via text: …") and bump its `last_mentioned`, rather than creating a second note. Check **every note in `/Trackers/Actions/`**, not just active ones — per [[Workflows/Open-Actions-Transcript-Steps]] Step 1, this is the same mandatory cross-check that applies to every path that adds an item (added 2026-07-21 after two near-duplicate m365-sync-investigation items slipped through).
- **A finding with its own named deadline is never note-only.** If a text contains an explicit commitment tied to a specific day/date ("I'll send X on Monday", "meeting Thursday at 3"), give it its own new note in `/Trackers/Actions/` with `status: active` — even when it's clearly a sub-step of a broader item already being tracked. Cross-reference the parent item with a `blocked_by`/`blocks` wikilink or a one-line pointer; don't bury the dated commitment inside the parent's Notes field, where it has no deadline field of its own and won't surface until the whole entry is re-read. (Trigger: Connor asked whether a Monday-follow-up commitment had become its own open action — it hadn't, it was folded into a long Notes blob on a broader On Hold item and was effectively invisible.)
- **Never change status to completed on your own.** When a text appears to COMPLETE an existing item, append the confirming text as a dated note (additive) AND record it as a **closure candidate**: set `status: closure-candidate` on the target note and append the evidence + what-to-verify to its Notes, and also surface it in the run report. This is what makes the candidate visible in the Closure Candidates view of [[Trackers/Open Actions.base]] even after the run report scrolls away — Connor said he can't read every sync's output. Connor decides whether to close (confirm/dismiss). See [[Workflows/Open-Actions-Reference]] → ### Closure Candidates — entry and exit. (A text can confirm one part of an item while a hidden sub-blocker remains open — see the 2026-06-24 Sunday-welcome-rep case, where the Derek confirmation arrived but the kids-coverage sub-question was separate.)

## Step 6: Ask before anything non-additive

Folding new items in is routine and needs no confirmation. **Ask first** before: merging or rewriting an existing tracker entry, archiving anything, or recording a finding that looks sensitive/confidential.

## Step 7: Report

In chat, report:
- Scan window (date range / ROWID range) and message count scanned
- Grace-relevant findings, grouped by person or event, each with the text source (name + date)
- What was folded into which tracker (with links)
- Any garbled/undecodable messages flagged (contact + timestamp)
- Any unresolved phone numbers flagged
- **Closure candidates** — tracked items a new text appears to complete (item name + evidence + what to verify), for Connor to confirm before they're closed. These are **also recorded as `status: closure-candidate`** on the target note (visible in the Closure Candidates view of [[Trackers/Open Actions.base]]) so they persist beyond this report (not just listed here).
- Any contradictions with existing tracker content that need Connor's call

## Step 8: Update the marker

Update the **## Last scan** marker below with the highest `ROWID` scanned and the run date, so the next run is incremental. Then **append a one-line entry to ## Run Log** (format defined there) — every run, even zero-finding or errored. The run *report* (Step 7) carries the detail; the log line only needs the counts.
