# Workflow: M365 → Obsidian Sync (Outlook email → trackers)

Governs the **M365 email sync** (see [[Trackers/Automation]] for the authoritative schedule). Since 2026-07-21 it runs on a **weekly floor plus on-demand** model, not a fixed daily cadence: the `grace-weekly-refresh` task fires it every **Monday 6 AM** as a safety net, and [[Workflows/grace-quick-refresh]] runs it whenever Connor sits down to do Grace work. The retired schedule was 8 AM / 12 PM / 4 PM daily — noted only because older run-log entries and cross-references still assume it. Folds new Outlook email — inbound **and sent** — into the existing trackers and event notes. Email is a first-class Grace source alongside transcripts and texts. Can also be run on-demand.

This is distinct from [[Workflows/weekly-synthesis]], whose source is *only* /Transcripts. This job is the sanctioned channel by which email reaches the trackers; weekly synthesis still never pulls from email itself.

## Source & window
- Use the **Microsoft 365 connector** (Outlook) — never Gmail (see [[CLAUDE.md]] EMAIL rule). Search **both Inbox and Sent Items**.
- **Window = (last successful run − 30 min overlap buffer) → now.** Read the **## Last successful run** marker at the bottom of this file and scan from **30 minutes before** that timestamp forward — not a fixed lookback keyed to the 8/12/4 schedule. This makes the window self-correcting: if a run is late, skipped, or errors out (task didn't fire, connector/mount was down), the next run's window automatically stretches back to cover the gap instead of silently losing it.
- **Why the 30-min overlap buffer (added 2026-07-15):** an email can arrive *inside* a run's window but not yet be returned by Outlook search — there's a lag of minutes between delivery and the message becoming searchable/indexed. Without a buffer, that run advances the marker past the email's timestamp, and the *next* run's window starts exactly where the marker left off — so the email falls into a dead zone between two windows and is **permanently skipped by both** (this is what dropped Derek's 7/14 Staff Mtg Recap: arrived 12:17 PM ET, ~17 min before the 12:34 marker, caught by neither the 12:34 nor the 4 PM run; found only because Connor asked). Starting each window 30 min *before* the marker re-scans that lag zone every run. **This is safe because of the dedup guardrail** (Guardrails §2): before adding anything, confirm the target note doesn't already reflect the email, and skip if it does. Overlap therefore costs a few redundant reads, never a duplicate entry.
- **No marker yet (first run ever), or marker unreadable/corrupted:** fall back to an 18h lookback from now, then record the marker as normal so subsequent runs are gap-based.
- **Sent email is often the most actionable** — it carries Connor's commitments, confirmations, and decisions.

## What to capture (priority order)
1. Commitments in sent mail ("works for me", "I'll follow up Thursday", "let's do X").
2. Confirmations / decisions reached in reply threads.
3. New deadlines or scheduled dates.
4. Information that updates or corrects something already in a note.

## Resolve, don't just log
When an email (or related calendar event) shows an existing Open Actions item is done — a "schedule X" whose meeting is now on the calendar / invite accepted, an action confirmed "submitted/sent/confirmed", or a "waiting on" item where the awaited party says "that's everything" — set `status: completed` on that note per [[Workflows/Open-Actions-Tracker]] (add a `resolved: YYYY-MM-DD` line citing the email/calendar evidence) and clear it from any other note's `blocked_by`, surfacing anything newly unblocked. Writing completion evidence into Status/Notes while leaving `status: active` is the exact gap to avoid. If completion is genuinely ambiguous, do **not** auto-close: update Notes and set `status: closure-candidate` on the target note (evidence + what to verify), so the likely-completion stays visible in the Closure Candidates view of [[Trackers/Open Actions.base]] for Connor to confirm or dismiss, rather than being buried in this run's report. See [[Workflows/Open-Actions-Reference]] → ### Closure Candidates — entry and exit.

## Guardrails
- Additive and conservative: skip an email rather than make a spurious update; leave an item in place rather than auto-close on an ambiguous signal.
- Avoid duplicates: **windows now overlap by design** (the 30-min buffer above, plus any fallback on first run / unreadable marker) — so this dedup check is load-bearing, not just a fallback safeguard. Before adding anything, confirm the target note doesn't already reflect the email and skip if it does.
- **Same duplicate-check applies to new Open Actions items, not just re-processing the same email twice.** Before creating a new note, check every note in `/Trackers/Actions/` (all statuses) for a substantively identical existing item and update that one instead — per [[Workflows/Open-Actions-Transcript-Steps]] Step 1 (added 2026-07-21 after two near-duplicate "missed m365-sync-run" items, for the 7/15 and 7/16 slots, were logged as separate headings instead of one item updated twice).
- **A finding with its own named deadline is never note-only.** If an email contains an explicit commitment tied to a specific day/date, give it its own new note in `/Trackers/Actions/` with `status: active` — even when it's clearly a sub-step of a broader item already being tracked. Cross-reference the parent item with a `blocked_by`/`blocks` wikilink or a one-line pointer; don't bury the dated commitment inside the parent's Notes field. (Same failure mode caught in the text-sync job on 2026-07-03 — mirrored here since email carries commitments just as often as texts.)
- Follow [[CLAUDE.md]] rules: never edit transcript bodies, never write to /Raw From Grace, ask before merging/archiving.

## Report
Emails processed (inbox + sent); notes updated and what changed; items set to `status: completed` (with evidence) and anything newly unblocked; emails that matched no note; and ambiguous completions left in place — now set to `status: closure-candidate` (visible in that view of [[Trackers/Open Actions.base]]; re-list them here too).

## Update the marker
After a run **completes successfully**, update the **## Last successful run** marker below with the run's completion timestamp (America/New_York, `YYYY-MM-DD HH:MM ET`). If the run errored, was interrupted, or a required mount (connector/Office folder) was missing partway through, **do not update the marker** — leave the old timestamp in place so the next run's window still covers the missed gap.

## Run Log
**Why this exists:** on 2026-07-13, a full-history audit found the sync had silently skipped two entire days (7/8, 7/12) — not a code bug, but the scheduled run getting cut off by Claude usage limits before it could do anything at all. A run that never fires or dies immediately leaves *zero* trace: no marker update, no error, nothing — indistinguishable from "the inbox was just quiet that day" unless something is written on every run that *did* execute. This log is that something.

**Every run that reaches this step** — success, or an error caught partway through — appends one line, oldest to newest:
`- <completion timestamp, America/New_York> | window <start>→<end> (marker|18h-fallback) | inbox N, sent M processed | updates K, dups J | OK` (or `| ERROR: <short reason>, marker not advanced` in place of the OK clause).

`dups J` = emails skipped because the target note already reflected them — i.e., the dedup guardrail firing. Since the 30-min overlap made windows overlap **by design**, dedup is load-bearing (Guardrails §2); this count makes it visible in the trace every run, so a silent dedup regression shows up as duplicate tracker entries *plus* a J that stopped moving, rather than being discovered by accident. Entries older than 2026-07-16 predate this field and won't have it.

Log the line even when N=M=0 and K=J=0 — a logged "found nothing" run is exactly what this is for, and it is not the same as a missing run.

**How to read it for gaps:** the schedule is 8 AM / 12 PM / 4 PM, so entries should land roughly every 4–8 hours. A run that runs but hits a quota/usage cutoff *before reaching this step* still won't appear here — but the **timestamp gap** between the previous entry and the next one that does land will be visibly wider than ~8 hours (often a full day or more, per the 7/8 and 7/12 precedent). That gap is the tell: cross-check the corresponding window against the inbox directly (as the 2026-07-13 audit did) rather than assuming a quiet log means a quiet inbox.

**Housekeeping:** keep the most recent ~100 entries (~a month at 3/day); when appending would exceed that, drop the oldest entry first so this section doesn't grow unbounded.

## Run Log health check (run by `grace-weekly-refresh`)
The Run Log only helps if someone actually looks at it. Rather than relying on Connor to notice a gap, the **`grace-weekly-refresh`** task (Mon 6:00 AM, see [[Trackers/Automation]]) checks it as a side duty alongside its Open Actions sweep, and turns a suspected gap into a visible, trackable item instead of a thing you'd only catch by reading a log no one reads.

**⚠️ Recalibrated 2026-07-27 for the weekly + on-demand cadence.** This check was written against the retired 8 AM / 12 PM / 4 PM schedule and counted entries *per calendar day*, expecting 3. Since 2026-07-21 the sync runs **weekly (Mon, via this task) plus on-demand (`grace-quick-refresh`)** — so most calendar days are *correctly* empty, and the old rules would have flagged a gap every single week. Both the per-day count and the ~20-hour staleness threshold are gone.

**Procedure:**
1. Read the **Run Log** section above. Take the **most recent entry's timestamp** (America/New_York).
2. **Primary check — did the weekly floor hold?** If the most recent entry is **more than 8 days old**, flag a **suspected missed run**. Eight days = one weekly cycle plus a day of slack, so a single late Monday doesn't false-positive but a skipped Monday does. On-demand runs are a bonus, never a substitute — their presence doesn't excuse a missing weekly entry, and their absence is not a fault.
3. **Event-week tightening.** If any /Events planning note's `date` is ≤3 days out, tighten the threshold to **4 days**. In an ordinary week a late catch-up costs nothing (the marker self-heals, zero data loss, per 7/15); in event week a delay can convert to a real-world miss — e.g. a registration or a volunteer cancellation arriving the morning of the event. Detection tightens exactly when delay is expensive.
4. **Secondary check — errored runs.** If the two most recent entries both carry `ERROR:` and the marker was not advanced, flag it regardless of age: the job is firing but failing, which the age check alone won't catch.
5. If nothing is flagged, do nothing further — this is not a report-every-week mechanism; it matches the refresh's "report only if something changed" behavior.
5. If something is flagged: check whether an **Active** item already exists in `/Trackers/Actions/` (visible in the Active view of [[Trackers/Open Actions.base]]) covering the same or an overlapping date range (search for "suspected missed m365-to-obsidian-sync run"). If so, just add a dated note to it instead of duplicating. If not, create a new note `/Trackers/Actions/Connor - Investigate suspected missed m365-to-obsidian-sync run(s).md`:

   ```
   ---
   status: active
   priority: P2
   owner: "Connor"
   added: {date of this sweep}
   deadline: "Unstated"
   last_mentioned: "{date of this sweep}"
   source: "[[Workflows/m365-to-obsidian-sync]] Run Log health check, {date of this sweep}"
   ---

   # Connor: Investigate suspected missed m365-to-obsidian-sync run(s)

   - **Priority**: P2 — data-integrity risk; a missed run can silently drop registrations or commitments (per the 7/8 and 7/12 precedent), but nothing else is blocked on it
   - **Source**: [[Workflows/m365-to-obsidian-sync]] Run Log health check, {date of this sweep}
   - **Added**: {date of this sweep}
   - **Deadline**: Unstated
   - **Status**: Open — Run Log shows {N} of {3 or expected} entries for {the flagged date(s)} (or: most recent entry is {timestamp}, {H} hours old). Suspected missed run around {window}. To verify: manually search Outlook Inbox + Sent Items across that window and cross-check against the trackers it would have touched — same method as the 2026-07-13 full-history audit.
   - **Last mentioned**: {date of this sweep}
   - **Notes**: none
   - **Blocked by**: none
   - **Blocks**: none
   ```

6. Report the flag (if any) alongside `grace-weekly-refresh`'s normal output. Resolving the item (confirming a real gap and backfilling, or dismissing a false alarm) is manual — this check only surfaces the suspicion, it never backfills on its own.

**Note on threshold:** under the old 3x-daily schedule the worst-case normal gap was overnight (~16h), so a flat time threshold couldn't distinguish "quiet night" from "missed slot" and a per-day count was needed. Under the weekly cadence the opposite is true: the expected gap *is* a week, so a flat threshold is now the right instrument and per-day counting is meaningless. The trade-off is coarser detection — a missed weekly run can go up to 8 days unnoticed, versus ~1 day before. That's the accepted cost of the cadence change (see [[Trackers/Automation]] § Operating note), mitigated by the fact that the marker-based window self-heals: a skipped run loses no email, it only delays processing.
