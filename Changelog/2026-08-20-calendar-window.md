# The refresh now pulls the calendar, and waiting-on items compute their own "when's the moment?"

## What went wrong

The 2026-08-20 quick-refresh report told Connor to raise the stalled [[Trackers/Actions/John Slye - FFEdL weekly topics + who delivers each message]] item **"in person at the Mon 8/24 session."** Two errors in one clause, and a third sitting beside it:

1. **No such occasion.** 8/24 4:00 PM is *"PCO/Rock Tutorial with Jennifer and Connor,"* organized by Kay Carter-Corker: **Kay, Jennifer Claffey, Connor. John Slye is not on it.** There is no scheduled event before that item's 9/6 `needs_by` where Connor and John are both attendees. The advice had no referent, and following it would have parked a load-bearing item behind a moment that never comes.
2. **No such channel.** "In person" — Connor works remotely. **This is the same correction he gave on 2026-08-10** about a hallway ask to Kay. It was recorded in memory then, and it still reached a *written vault note* ten days later.
3. **A hypothesis that was free to check.** The same run had already written *"the Derek sync may have moved to Mondays"* into the new Deep and Wide note, inferred from Connor's text *"all of section 2 is good for Monday."* Outlook: the recurring `Weekly Sync` is **Tue 8/25 4:00 PM ET**, same slot as 8/18. Nothing moved — he was setting himself a read-by a day early.

## Root cause, which is not a discipline problem

[[Workflows/Open-Actions-Tracker]] referenced the calendar as an evidence source in **four separate places** — *"Calendar (if accessible)"*, *"a calendar hit"*, *"a confirmed future date/meeting"*, *"asked X to put it on the calendar"* — and **no phase of either refresh routine ever fetched it.** Outlook was present in the procedure as a *permission* and absent as a *fact*. When a procedure implies a fact should inform judgment and the fact is not there, the gap gets filled by inference.

So the fix could not be a fifth sentence telling a future run to check the calendar. **Three times now this vault has learned that documenting a fix looks identical to making one**: `immutable=1` was corrected in the text-sync workflow and not in `resolve-phone.py` (the PHANTOM defect found earlier this same run, [[Changelog/2026-08-20-resolve-phone-wal-phantom-fix]]); the 2026-07-17 "add `phone:`-property notes as a resolution source" fix was documented and never actually worked; and the 8/10 remote-work correction was written to memory and violated anyway.

## What changed

**1. [[Trackers/Calendar-Window]] — new, regenerated by Phase 1 of both refreshes.** One `outlook_calendar_search` call, next ~3 weeks, real events with attendees. ~2 KB. The daily self-blocks (`Morning Availability`, `Afternoon Availability`, `Daily FTJ Conflict`) are excluded — they have no attendees and were **47 of the 57 events** in the first window; `calendar-window.py` drops them again by subject as a second line of defence.

**2. [[Workflows/calendar-window.py]] — new.** Parses that file and answers the question directly:

```
python3 "Workflows/calendar-window.py" --who "John Slye" --before 2026-09-06
  → John Slye: NO shared meeting before 2026-09-06. There is no occasion to
    raise it at; the channel is text, then call.
```

Name→email comes from the **Office `Staff Contact List.xlsx`** (authoritative), plus a local-part match against addresses actually present in the window — which is what catches **Kay organizing from `kcartercorker@gmail.com`** while the staff list holds `kay.cartercorker@trygrace.org`. `--check` reports staleness (>4 days) and a window running out.

**The status vocabulary is the point of the whole thing:** `ok` / `none` / `unknown` / `no-window`. **`unknown` is never allowed to collapse into `none`** — that conflation ("I couldn't find it, therefore it isn't there") is precisely the defect that made `resolve-phone.py` condemn a real number as PHANTOM this morning. Two instances of the same mistake in one run was worth designing against explicitly.

**3. [[Workflows/actions-index.py]] — every waiting-on item now carries `next w/ <person>: <date>`**, and a new candidate list, **WAITING-ON WITH NO SHARED OCCASION**, names the items where no meeting exists before the item's own date. First run, all 9 waiting-on items resolved:

- **Derek ×3 → 2026-08-25** (the Tuesday sync)
- **Kay ×3 → 2026-08-24** (the Rock/PCO tutorial)
- **John Slye → NONE before 9/06** · **Heather Noble → NONE before 9/03**
- **Skylar → unknown** (single first name, not on the staff list — reported honestly rather than silently)

**One bug caught by measurement during the build, and it mattered:** the first version compared against `needs_by` even when that date had already passed, so the Kay Rock↔PCO item (`needs_by` 2026-08-15, blown) reported *"NONE before 2026-08-15"* — while Connor in fact has a Rock/PCO session with Kay on **8/24**. An expired date was suppressing the single most useful answer in the feature. A passed limit is now ignored and labelled.

**4. Both refresh workflows + [[Trackers/Automation]]** record the pull as a Phase 1 step, and the weekly task's safety kernel gains rule 9: never assert a meeting, query the window, and `unknown ≠ none`.

## What was deliberately not built

Connor was offered a **banned-phrase lint** (grep new note lines for `in person`, `in the room`, `swing by`, and for `raise it at X` without a verification tag) and declined it. Recorded here so it is not re-proposed. The honest case against it is the one made when offering it: it catches **vocabulary, not false beliefs** — it would have caught "in person" and sailed straight past "John is at the 8/24 session."
