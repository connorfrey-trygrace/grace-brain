# Refresh — Run Log

Created 2026-08-11. One line per `grace-quick-refresh` / `grace-weekly-refresh` run, recording **where the wall-clock actually went**. **This file is append-only history — it is not read during a normal run**, only when a refresh feels slow or a regression needs proving.

**Why it exists:** Connor asked why the 2026-08-11 quick refresh took ~30 minutes, and nothing in the vault recorded elapsed time. The answer had to be reconstructed from file mtimes, which show only writes — so a 48-minute stretch of pulling and analyzing appeared as a blank gap, indistinguishable from an idle one. Per-phase totals make the next answer a lookup instead of a forensic exercise.

---

**Format** — one line, oldest → newest, appended after Phase 3:

`- <finish timestamp, America/New_York> (quick|weekly) | total Xm | p0 Xm (<transcripts>) | p1 Xm | p2 Xm | p3 Xm | in: <N emails, N msgs, N transcripts> | out: <N notes / N KB> | <anything that dominated the run> | OK`

- 2026-09-11 14:22 ET (quick) | total 11m | p0 <1m (0 transcripts) | p1 3m (calendar reused, fresh from 12:11 ET; text scan + email sync parallel) | p2 3m (writes + stamps + clock-check) | p3 4m (sweep — 6 body reads/edits) | in: 0 emails, 8 msgs in scope, 0 transcripts | out: 11 notes touched / ~3 KB | report 1m | tokens 16.4M total, peak context 243k/1.0M (24%) | dominant cost: sweep body reads (candidate-list follow-through) | OK

Measure with `date '+%s'` at the top of Phase 0 and at each phase boundary — four stamps, **plus a fifth after the report is written** (added 2026-08-12). **Report measured minutes only.** If a stamp was missed, write `unmeasured` for that phase rather than a guess; a fabricated number here defeats the file's whole purpose. Note anything unusual — a mid-run procedure repair, a mount hunt, a retried connector, one oversized note — in the second-to-last field. Those are real minutes and they are invisible otherwise.

**Two fields added 2026-08-12 — additive only, nothing existing changes:**

- `report Xm` — elapsed from the end of Phase 3 to the finished report. On 2026-08-12 this was **~8m, more than Phase 3**, and it was invisible because instrumentation stopped at the last phase. A phase that isn't stamped can't regress in a way anyone notices.
- `wrote N KB` — **bytes actually added**, distinct from the existing `out:` field. `out:` counts the *size of the files touched*, which overstates cost by an order of magnitude: a 27 KB note that received a one-line append shows as 27 KB when generation cost ~200 bytes. Wall clock in this system tracks **tokens generated**, so bytes-written is the field that correlates with elapsed time; `out:` stays because it still answers "how much of the vault did this run reach."

**One field added 2026-09-02 — additive only, nothing existing changes:**

- `tokens ... | peak context ...` — output of `python3 "Workflows/usage-report.py" --session-id <uuid> --since <phase-0 stamp> --until <final stamp>`, appended verbatim. Total token traffic for the run, plus how full the context got on its single fullest turn, as a % of that model's context window. Reuses the same two stamps `elapsed`/`wrote` already require — no new measurement, just a new read of what those stamps bound. See the script's docstring for what "total" vs "peak context" mean and why the per-model window table is a self-correcting guess, not a verified constant.

*Measured 2026-08-12, for calibration:* copying the 349 MB `chat.db` costs **2.38s**; opening it with `file:…?immutable=1` and querying costs **0.01s**; `actions-index.py` over all 139 notes costs **0.047s**. **Disk is not the bottleneck and a run should never be explained by I/O** without a measurement saying so — the 2026-08-11 13:46 entry's "a minimum-window guard would have paid for itself" claim was retracted on this basis.

Housekeeping cap: keep the most recent ~90 entries; older ones move to an archive file rather than being deleted.
