Austin: this is the pattern the rest of the fleet should converge on. Verified live: the 7/16 Run Log entries show windows starting 30 min before the marker (07:47 start against an 08:17 marker), so the buffer isn't just documented — it's running.
- **Boris's compounding loop is demonstrably real.** Workflow changelogs cite run incidents and feed rules back in: the timezone fix (text-sync, 6/25, after a mislabeled 8:43 AM text), the "a dated commitment is never note-only" rule (7/3, mirrored into *both* syncs), the re-resolution watchlist (6/26, after Brandon Geddes/Simba Kanjanda sat unknown), the marker window + Run Log + health check trio (7/13, after the 7/8 and 7/12 silent gaps). These skills are compounding, not decaying.
- **Ash's standard — someone actually read the traces — is met at the top.** The 2026-07-13 full-history audit read the Run Log's gaps by hand and produced three structural fixes. The 7/15 dead-zone incident (Derek's Staff Mtg Recap, arrived 12:17 PM, missed by both adjacent windows) became the overlap buffer within a day. That's the debugging loop Ash describes, working.
- **Cat's proactivity bar is met where it matters most.** The pinned Closure Candidates queue at the top of [[Trackers/Open Actions.base]] exists precisely because Connor said he can't read every run report — likely-completions now come to him in a place he already looks, with a confirm/dismiss lifecycle. - **Karpathy's leash is visible throughout.** Syncs are additive-only; the text scan *never* closes items; the email sync auto-closes only unambiguous completions and routes everything else to Closure Candidates; the Sky exclusion is enforced at the SQL level, not read-then-ignore; the world-cup Rock sync ends with a verify step (recompute counts, confirm totals match Rock). - **The inventory is honest.** All 7 Grace tasks in [[Trackers/Automation]] match the live scheduler on id, cron, and enabled state. The daily-over-hourly preference is honored, and the one bend (world-cup sync, a second daily Rock touch) is argued explicitly in the 7/14 changelog rather than slipped in — exactly how a documented preference should be treated.

## Findings

### 1. Observability is concentrated in one job — four of seven are dark (Ash, Austin) — Tier 2
**Evidence:** Only `m365-to-obsidian-sync` (Run Log), `grace-text-scan` (the `## Last scan` history), and `world-cup-rock-volunteer-sync` (dated bullets in the registrant tracker, including "no changes" days) leave a per-run trace. `event-checklist-autocopy`, `daily-stale-sweep`, `weekly-synthesis`, and `derek-weekly-sync-agenda` leave nothing when they fail — and two of them ([[Workflows/event-checklist-autocopy]], `daily-stale-sweep`'s SKILL.md) are explicitly report-only-if-something-happened, so silence is indistinguishable from silent death.

**Why it matters, per job:**
- `event-checklist-autocopy` has no run log, so a silent failure the week before an event is invisible — the exact failure mode the m365 Run Log was built to catch (see [[Trackers/Automation]] changelog 2026-07-13). Its receipt (the planner file) only exists when there's an event ≤7 days out, so most days there is *nothing* to check.
- `daily-stale-sweep` is the **watcher with no watcher**: it's the job that reads the m365 Run Log for gaps. If *it* dies silently (usage limits — the same mechanism that killed the 7/8 and 7/12 m365 runs), both the stale sweep *and* the m365 gap detection go dark at once, and nothing notices.
- `weekly-synthesis` and `derek-weekly-sync-agenda` at least have self-evident receipts (the Friday note, the Tuesday agenda) — but nothing *checks* the receipt landed, and for the agenda, the failure becomes visible exactly when it's too late to matter.

**Proposed change (Tier 2):** don't add a new watchdog job (Boris: fold it into what exists). Extend the daily-stale-sweep's existing health-check duty from "read the m365 Run Log" to "read the scheduler": one `list_scheduled_tasks` call, compare each Grace task's `lastRunAt` against its cadence, flag any job overdue by more than one full cycle into [[Trackers/Open Actions.base]] using the same flagged-item pattern already defined in [[Workflows/m365-to-obsidian-sync]] §Run Log health check. Then close the loop on the watcher itself: the Friday `weekly-synthesis` health check (which already exists per [[Workflows/system-audit]]) verifies the sweep ran that week. Two additive sentences in two existing prompts; no new job, no new log files.

### 2. The health check doesn't run on the weekend the World Cup happens (Austin, Ash) — Tier 2 + one immediate action
**Evidence:** `m365-to-obsidian-sync` runs 7 days/week and is the channel that feeds World Cup registration notifications into [[Archive/2026-07-19-World-Cup/World-Cup-Registrants]]. Its gap-detector, `daily-stale-sweep`, runs **Mon–Fri 5:32 PM** ([[Trackers/Automation]]). A sync failure on Saturday 7/18 or Sunday morning 7/19 would first be flagged **Monday 7/20 at 5:32 PM — after the event**. Registrations have been arriving daily this week (+3 on 7/16 alone, per the registrant tracker's Count line).

**Proposed change:** immediate and cheap — Connor runs the m365 sync (or just the health check) on-demand Saturday evening and Sunday ~noon before the 2:30 PM doors. Longer-term (Tier 2): either extend `daily-stale-sweep` to 7 days, or add an "event-weekend" rule — sweep runs weekends only when an /Events note is ≤2 days out. The panel leans to the second: it matches Connor's documented lean-cadence preference instead of paying for 52 weekends to cover the ~4 that matter.

### 3. Two task prompts have drifted from their workflows — the two-sources-of-truth problem (Boris, Karpathy) — Tier 2
**Evidence:** the m365 job established the house pattern: the SKILL.md is a minimal safety kernel that says *"the workflow file is the source of truth — read it first."* The other two content-bearing prompts predate it and duplicate procedure inline, and both have already drifted:
- `~/Claude/Scheduled/grace-text-scan/SKILL.md` step 5 resolves contacts via the Office list, Vendors, and spelling rules — it **omits [[Contacts/Phone-Index]] (check-first cache) and Step 3.5 (the re-resolution watchlist pass)** that [[Workflows/text-message-sync]] added on 6/25–6/26. The "workflow file wins" line has masked this so far, but the prompt now actively describes an older procedure.
- `~/Claude/Scheduled/event-checklist-autocopy/SKILL.md` restates the *entire* workflow inline — every future edit must now be made twice or the copies diverge.
- Both prompts still call the vault **"Obsidian Vault 1"**; it is "Grace Brain". Harmless today, confusing on the day a mount genuinely fails and someone debugs from the prompt text.

**Proposed change (Tier 2):** migrate both prompts to the m365 kernel pattern (5–8 safety lines + "read the workflow file and follow it exactly"), and fix the vault name. Karpathy's framing: the workflow file is the spec; a prompt that restates the spec is a second spec, and two specs always eventually disagree — as the text-scan one already does.

### 4. The text-scan's run history is unbounded and over-clever (Boris, Ash) — Tier 2
**Evidence:** [[Workflows/text-message-sync]] is ~29k tokens for 156 lines because the `## Last scan` section carries paragraph-length run entries back to 6/24 under an improvised key chain (`prior_run_PRE0716`, `prior_run_PRE0714b`, … `prior_run_b`). The m365 Run Log solved the identical problem with one-line entries and an explicit ~100-entry housekeeping cap ([[Workflows/m365-to-obsidian-sync]] §Run Log); this section has no cap and every daily run must read the whole file to find the marker.

**Nuance (Ash):** this section is *good trace data* — it's the reason the text scan isn't on the dark-jobs list in Finding 1. Don't delete the history; move it. **Proposed change (Tier 2):** adopt the m365 format — a two-line marker (`last_rowid` / `last_run`) plus a capped one-line-per-run log; relocate the existing rich entries to an archive note under /Archive (never delete, per house rules).

## Where the panel disagrees

- **Detection vs. recovery (Finding 8).** Karpathy wants single-slot misses flagged: never delegate what you can't verify, and an undetected slip rate is unverified delegation. Austin and Boris push back with the receipts: the marker design already made single misses harmless (7/15 proved it — zero data lost), the current threshold was set deliberately to avoid false-positiving every quiet overnight (§"Note on threshold"), and per Austin's cautionary tales the expensive failure is alarms people learn to ignore. Ash splits it: keep the threshold, but the event-week tightening is worth it because event weeks are when a 4-hour delay converts to a real-world miss. The panel presents the event-week variant, not the always-on one.
- **Add a watchdog vs. delete complexity (Findings 1, 4, 5).** Cat's instinct is more routine coverage (scheduler-wide heartbeat, weekend sweeps); Boris's is that the system's edge is its smallness, and this audit should *remove* more than it adds — retire the world-cup sync on schedule, put the text-scan log on a diet, collapse three m365 prompt copies toward one, and only then extend the sweep. They converge on the mechanism (no new job; extend `daily-stale-sweep`) but not the appetite; the Top 3 below reflects Boris's ordering inside Cat's proposal.
- **Marked extrapolation:** the panel's personas argue from their documented public positions (Austin's four rules, Cherny's bottleneck-first simplicity, Karpathy's specs/verification writing, Wu's proactivity remarks, Ash's traces workshop). Applications to this vault are the panel's inference, not things these people have said about Grace Brain.
